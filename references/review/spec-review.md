# spec-review.md — 规格评审（相 1）

对相 1 起草好的 `tasks.json` 做一次性规格独立评审。评审的是"计划本身是否合理、可执行、右尺寸"，不评审代码（代码还没写）。
本文件自包含、零外部依赖；装了 gstack 时可回退调 `gstack/plan-eng-review` 取更深维度（见文末兜底）。

## (a) 工程原则（评审规格时据此发问）
- DRY：同一职责在多个任务/文件里重复出现，应收敛成一处或一个共享任务。
- 右尺寸 diff：偏好干净表达变更的最小改动；但地基已坏时不要把必要重写压成小补丁，该"推翻重来"就明说。
- boring by default：优先成熟方案，新基础设施/新依赖是要慎花的"创新额度"，框架有内建就别自己造。
- essential vs accidental complexity（Brooks）：加任何东西前先问"这是在解真问题，还是在解我们自己造出来的问题？"
- blast radius：每个任务问"最坏情况是什么、会波及多少系统/人？"，高波及面的任务单独隔离、加护栏。
- 可逆性：偏好可回滚、可增量上线的设计，让"做错的代价"尽量低；不可逆动作（删数据/改生产）必须显式标注。
- 显式优于取巧，edge case 宁多勿少；完整实现优于走捷径（AI 辅助下补全的成本远低于人力估算）。

## (b) 规格校验项（task-harness 原有）
- 依赖图无环：任务间 `depends_on` 构成 DAG，不存在循环等待。
- 路径归属清晰：每个任务声明的文件/路径不与其他任务重叠冲突，归属唯一可判。
- verify 可执行且客观可判：每个任务的 `verify` 命令能真正跑起来，退出码/输出能客观判定通过与否，不是"人肉看一眼"。
- 任务粒度合理：一句话能说清一个任务的范围；说不清的要拆，琐碎到不值一个任务的要并。
- ponytail 视角：有没有伪任务（不产出实际价值）？能不能复用已有代码/流程而不是新建并行实现？能不能拆得更小、范围更收？

## (c) 输出
先逐条列出规格问题（`[原则|校验项] task-id 或 spec — 问题一句话 → 建议一句话`，无则 "No issues"），最后固定输出恰好一行契约：

`HARNESS_REVIEW: pass|fail | spec | <一句理由>`

判定：依赖图有环、路径归属冲突、存在无法客观判定的 verify、或有实质伪任务/越界扩张 → `fail`；否则 `pass`。task-id 处用 `spec`（整体规格），或换成对应的具体任务 id（针对单任务复评时）。

## 兜底（可选）
规格复杂到内联原则不足以判定且本机装有 gstack 时，可回退调 `gstack/plan-eng-review` 取更深维度，结论仍按上面的契约行回收；两者都不可用时如实标 `blocked`，绝不伪造 pass。
